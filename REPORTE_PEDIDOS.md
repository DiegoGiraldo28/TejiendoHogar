## 2. Decisiones de implementación (Etapa A)
- **Llaves foráneas:** se usa `PROTECT` en todas (equivale al RESTRICT del esquema). `DetallePedido.producto` lleva PROTECT para que `catalog.services.eliminar_producto` siga mostrando «tiene pedidos asociados».
- **`ck_pedido_pago_exitoso`:** el esquema usa `COALESCE(pago, '') = 'Exitoso'`. En Django se expresa como `pago IS NOT NULL AND pago = 'Exitoso'`, que es equivalente. Sin el `IS NOT NULL`, un pago nulo pasaría el CHECK por la lógica de tres valores de SQL.
- **Disponibilidad:** los Disponibles se validan con `validar_disponibilidad`. En los Sobre pedido se suman los requerimientos de `calcular_requerimiento` de todas las líneas por insumo, para que dos productos que comparten un insumo no lo cuenten dos veces.
- **Rechazos:** la validación de existencias de `crear_pedido` y de `pagar_y_confirmar` corre dentro de `transaction.atomic()`. Si falta algo, se lanza una excepción interna, el bloque se revierte y el `RechazoPedido` se guarda **después**, fuera del bloque revertido. Si faltan unidades de un Disponible, `crear_pedido` lo registra como `Stock_insuficiente`, en lugar de cortarlo antes con el tope, para que quede en la métrica.
- **Motivo cuando faltan ambos:** si faltan stock e insumos a la vez, se registra `Stock_insuficiente`, porque se valida primero.
- **Bloqueos:** `pagar_y_confirmar` y `cancelar_pedido` bloquean primero el pedido (`select_for_update`) y después los productos y sus insumos, en orden de llave primaria. Los descuentos usan `UPDATE ... WHERE cantidad >= requerido` con `F()`, así que nunca quedan valores negativos.
- **Doble envío:** si el pedido bloqueado ya está Confirmado o en un estado posterior, se lanza `PedidoYaConfirmado` («Tu pedido ya fue confirmado»), que la vista mostrará como mensaje informativo. Si está Cancelado, el mensaje es «ya no está pendiente de pago».
- **Desglose de la fecha:** se calcula a partir de lo guardado: `cola = (estimada − fecha de confirmación local) − días propios − alistamiento`. Así siempre suma la fecha guardada. El esquema no guarda cuántos pedidos había en la cola, por eso no se muestra «(N pedidos antes)».
- **`preparar_pedido_desde_bolsa`:** reutiliza el Pendiente de la sesión solo si es de la misma Cliente, sigue Pendiente y tiene las mismas líneas y la misma entrega. Si algo cambió, crea uno nuevo y **después** cancela el anterior, para que un rechazo no deje a la Cliente sin ninguno. Un Pendiente ajeno, pagado o cancelado se ignora y no se toca.
- **Método de pago:** la pasarela recibe solo `{"simular_exito": bool}`. El método elegido no se guarda.

CREATE OR REPLACE FUNCTION fn_validar_transicion_pedido()
RETURNS trigger AS $$
BEGIN
    IF NEW.estado = OLD.estado THEN
        RETURN NEW;
    END IF;

    IF (OLD.estado, NEW.estado) IN (
        ('Pendiente',      'Confirmado'),
        ('Pendiente',      'Cancelado'),
        ('Confirmado',     'En_preparacion'),
        ('Confirmado',     'Cancelado'),
        ('En_preparacion', 'Listo'),
        ('Listo',          'Entregado')
    ) THEN
        RETURN NEW;
    END IF;

    RAISE EXCEPTION 'Transición de estado no permitida: % -> %', OLD.estado, NEW.estado
        USING ERRCODE = 'check_violation';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_pedido_transicion_estado
    BEFORE UPDATE OF estado ON pedido
    FOR EACH ROW EXECUTE FUNCTION fn_validar_transicion_pedido();
